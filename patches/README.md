# ZMK 패치

이 폴더의 패치는 **ZMK 자체**를 고칩니다. `build.sh` 가 빌드할 때마다 깨끗한 트리에 다시 적용합니다.

`.zmk-workspace/` 는 `.gitignore` 대상이라, 거기서 손으로 고친 것은 다음 체크아웃 때 사라집니다. 이 리포지토리에 남는 패치가 ZMK 변경을 지킬 수 있는 유일한 방법입니다.

⚠️ **`build.ps1`(윈도우)은 패치를 적용하지 않습니다.** 사용자가 직접 관리하는 ZMK 체크아웃을 쓰기 때문에, 남의 트리를 말없이 고치는 대신 적용되지 않았다고 경고만 합니다. 경고에 적힌 `git apply` 명령을 직접 실행하면 됩니다.

## 왜 패치를 감수하는가

ZMK 는 이미 `build.sh` 에서 리비전이 고정돼 있습니다. `led_breath.c` 가 공개 API 가 아닌 내부 심볼에 손을 대기 때문인데, 그러니 이 리포지토리는 이미 특정 ZMK 에 묶여 있습니다. 패치는 그 결합을 새로 만드는 게 아니라 이미 있는 것 위에 얹는 것입니다.

가능하면 devicetree 로 해결하고, 안 될 때만 패치를 씁니다. 예를 들어 마우스 동작의 `display-name` 은 속성이라 실드 키맵(`modu.keymap`)에서 덮어썼고, 패치가 필요 없었습니다.

## 목록

### 0001-pointing-parameter-metadata.patch

`&mmv`(마우스 이동)와 `&msc`(마우스 스크롤)에 파라미터 메타데이터를 붙입니다.

ZMK 는 이 둘에 메타데이터를 선언하지 않습니다. 그래서 Studio 클라이언트가 **어떤 값을 넣어야 하는지 알 수 없습니다** — 키에 걸 수는 있지만 방향을 고를 수 없고, 이미 걸린 것도 방향 없이 그려집니다. 나머지 21개 동작은 전부 선언되어 있습니다.

⚠️ 메타데이터를 인스턴스별로 붙입니다. `&mmv` 와 `&msc` 는 같은 드라이버(`zmk,behavior-input-two-axis`)를 공유하지만 숫자가 다릅니다 — `MOVE_UP` 은 600, `SCRL_UP` 은 10 을 같은 32비트 x/y 쌍에 담습니다. 드라이버에 static 목록 하나를 두면 둘 중 하나에게는 틀린 값 네 개를 주게 됩니다. `get_parameter_metadata` 콜백이 `device` 를 받으므로, 인스턴스의 축 코드(`INPUT_REL_WHEEL` 여부)로 목록을 고릅니다.

⚠️ 네 방향은 **전체 파라미터 공간이 아닙니다.** param1 은 부호 있는 x·y 를 32비트에 담으므로 어떤 속도·방향도 유효합니다. 손으로 `MOVE(300, 300)` 을 쓴 키맵도 그대로 동작하며, 다만 클라이언트가 제시하는 선택지에 없을 뿐입니다.

상류(ZMK)에 올릴 만한 변경입니다. 올라가면 이 패치는 지울 수 있습니다.
